## Origins and routing

Use `https://app-api.cobaltlauncher.com` for application requests and `wss://app-api.cobaltlauncher.com/social/ws` for realtime. The separate `/v1` API uses `https://api.cobaltlauncher.com`.

Internal routes have no common `/api` or `/v1` prefix. For example, playtime is `POST /sync`, saves settings are `GET /settings`, and discovery search is `GET /search`.

These origins are configured defaults, not a live availability check. Cobalt ID uses `http://localhost:8080` on localhost, optionally overridden by local storage key `cobalt-id-api`. On other hosts it reads the `cobalt-api` meta tag, falling back to the application origin.

The router enforces the public hostname for the `public` module and `/v1/health`. Only the historical `/health` route checks the application hostname; ordinary internal routes do not have that host guard. Host mismatches return a plain-text `404`. The incoming port is stripped before comparison, so a configured local hostname must be `localhost`, not `localhost:8080`.

## Authentication labels

| Label in this reference | Credential |
| --- | --- |
| Public | No credential required. A supplied bearer token is ignored. |
| User | `Authorization: Bearer ID_TOKEN` from a Cobalt session. |
| Optional user | Omit the header for anonymous access; a supplied token must validate. |
| Admin | User bearer token whose Cobalt profile has `isAdmin: true`. |
| API key | `Authorization: Bearer cbl_...`; only for routes explicitly using API-key auth. |
| Bypass | Configured shared bypass credential in `X-Bypass-Key` or as a bearer token. It is not an app-user credential. |

User, admin, and API-key authorization also require an existing Cobalt profile and reject banned accounts with `403 ACCOUNT_BANNED`. A provider token alone is insufficient if the profile has not been created: `401 profile not found`. Complete a Cobalt sign-in flow to establish it.

The HTTP authorization layer does not authenticate cookies or read `X-Cobalt-Key` as a credential, even though that header is allowed by CORS. WebSockets additionally accept `?token=ID_TOKEN` if no bearer token was supplied.

## JSON and naming

Send `Content-Type: application/json` with JSON bodies. Upload routes take raw bytes, not multipart forms or JSON. A JSON request must contain exactly one JSON value and fit within 1 MiB.

Names are case-sensitive on the wire and intentionally vary across features: `gameId` in catalog records, `game_id` in playtime totals, `authorizationUrl` for browser authentication, and `authorizationURL` for Minecraft.

Responses have no universal envelope. Read the exact object or array documented for your endpoint. Stored optional metadata can be `null`. Catalog endpoints decode `platforms` and `genres` to arrays; discovery endpoints can retain JSON-encoded strings. Do not apply one game decoder to every endpoint.

String limits described as bytes follow the server's UTF-8 byte length checks. Profile display name and bio limits count Unicode code points. Most timestamps are RFC3339 strings; DM `ts`, `updatedTs`, `before`, and `since` use Unix milliseconds. Rate-limit reset headers use Unix seconds.

Most successful handlers return `200`; other success statuses are specified per endpoint. A success response does not always contain tokens: registration and email verification can return `202`.

## Errors and limits

Ordinary handler errors return:

```json
{"error":"not found"}
```

| Status | Meaning and client handling |
| --- | --- |
| 400 | Invalid fields, unsupported values, expired/consumed handoff, or identity-provider rejection. Show the message; correct input. |
| 401 | Missing/invalid credential or revoked refresh session. Attempt one coordinated refresh for an authenticated request. |
| 403 | Banned account, insufficient role, missing friendship, or invalid bypass credential. Refresh does not fix permissions. |
| 404 | Missing resource, unavailable finished artwork, wrong host, or disabled module. |
| 409 | Conflicting username/link/key limit or a Minecraft account needing relinking. |
| 413 / 415 | Oversized body / unsupported upload format. |
| 429 | Rate limit exceeded; honor `Retry-After`. |
| 500 | Unhandled server failure, returned as `internal server error`. |
| 501 | Unsupported identity capability or an unimplemented versioned data source. |
| 502 / 503 / 504 | Upstream failure / unavailable configuration or capacity / timeout. |

Router 404/405 responses, CORS rejections, and recovered panics need not use the JSON envelope. Check `Content-Type` before decoding an error and preserve its HTTP status. Network/CORS failures can have no HTTP status available to browser code.

All responses receive `X-Request-ID`. Default per-client-address limits are 60 requests/minute across the auth module, 300 across discovery, and 600 across catalog. Each module shares its own limiter across its routes, including callbacks. These limits are configurable, and are not separate allowances per endpoint.

Rate-limited routes expose `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, and `Retry-After`. Ordinary request capacity defaults to 256 concurrent requests; overload returns `503 {"error":"server is busy"}` with `Retry-After: 1`. Probes and WebSocket upgrades have separate lifecycles.

## Browser behavior

CORS allows configured origins and methods `GET, POST, PATCH, PUT, DELETE, OPTIONS`. Allowed request headers are `Content-Type, Authorization, X-Cobalt-Key`. Custom save metadata headers and `X-Bypass-Key` are not included, so cross-origin browser requests using them fail preflight unless the deployed boundary provides additional support. Native clients do not have browser CORS restrictions.

## Health

Public `GET /livez`, host-checked `GET /health`, and host-checked `GET /v1/health` return `{"status":"ok","ts":<Unix milliseconds>}`. Public `GET /readyz` returns `{"status":"ready"}` or `503 {"status":"not_ready"}`, with `Cache-Control: no-store`.

## Retry semantics

Do not automatically replay every failed request. Sending a DM creates another message; reacting toggles a reaction; reading invites consumes them; claims are single-use; uploads overwrite the current save. A timeout can occur after a change was committed.

Playtime sync is repeatable only when you keep a stable session identifier and cumulative totals. Read the feature-specific rules before enabling automatic mutation retries.
